# 복셀 스냅샷 전송 중 발생한 복제 지연

복셀 스냅샷과 변경 히스토리를 짧은 시간에 대량으로 전송하자 새로운 액터의 생성과 컨트롤러 소유권 반영이 클라이언트에서 늦어지는 문제가 발생했다.

서버에서는 액터가 정상적으로 생성됐지만 클라이언트에 필요한 정보가 제때 도착하지 않았다.
이번에는 복셀 데이터의 전송량과 클라이언트 적용 작업을 나누어 개선했다.

## 과도한 청크 전송과 초기 복제 지연

문제를 분석하면서 대량의 복셀 청크 전송이 네트워크 대역폭을 점유하는 상황을 확인했다.
액터 채널 생성과 초기 복제에 필요한 정보가 전송 대기열에서 지연되면서, 클라이언트에서 액터와 소유권을 확인하는 시점도 늦어졌다.

이 현상은 네트워크 포화 시 언리얼이 액터 생성 복제를 일괄 차단한다고 표현하기보다,
제한된 네트워크 예산과 전송 대기 때문에 액터 채널 생성 및 초기 복제가 지연되는 문제로 정리하는 편이 정확하다.

서버의 액터 생성 여부와 클라이언트에 해당 액터가 보이는 시점을 구분해서 볼 필요가 있었다.

## IsNetReady를 이용한 전송량 조절

`IsNetReady`를 이용해 현재 연결이 추가 데이터를 전송할 수 있는 상태인지 확인했다.
단순히 고정된 개수의 청크를 계속 보내는 대신, 전송 가능 상태가 유지되거나 회복되는 흐름에 따라 한 번에 보내는 청크 수를 조절했다.

| 연결 상태 | 전송량 조절 |
|---|---|
| 전송 가능 상태가 일정 시간 이상 회복되지 않음 | 혼잡한 상태로 판단해 청크 수 감소 |
| 전송 가능한 상태가 안정적으로 유지됨 | 청크 수 증가 |

이번 구현에서는 연결의 전송 가능 여부를 전송량 조절 신호로 활용했다.
복셀 데이터가 네트워크를 독점하지 않도록 보내는 속도를 조절하는 것이 목적이었다.

## 전송 시간과 액터 반영 결과

동적으로 전송량을 조절한 뒤 전체 스냅샷 전송 시간은 이전보다 길어졌다.
대신 테스트에서는 스냅샷 적용 직후 새로운 액터의 생성과 소유권 정보가 정상적으로 반영되는 모습을 확인했다.

이 결과가 스냅샷 완료를 액터 복제의 필수 조건으로 만든다는 의미는 아니다.
이번 기록에서 관찰한 결과는 대량 전송의 부하를 낮춘 뒤 액터 반영 지연이 개선됐다는 것이다.

복셀 데이터만 빨리 보내는 것보다 다른 복제 데이터도 함께 전달될 수 있도록 전송량을 조절하는 것이 필요했다.

## 클라이언트의 복셀 생성도 분산

네트워크 전송량을 줄여도 수신한 스냅샷을 한 번에 복셀로 생성하면 클라이언트에 프레임 부하가 집중될 수 있었다.
수신 데이터로 복셀을 생성하는 작업도 청크 단위로 나누고 비동기 처리와 프레임별 작업 분산을 적용했다.

전송 측에서는 네트워크 작업량을 조절하고, 수신 측에서는 실제 복셀 생성 작업량을 분산하는 방식이다.

## 처리 흐름

1. 서버에서 복셀 스냅샷과 변경 히스토리를 청크 단위로 구성한다.
2. `IsNetReady`로 현재 연결의 전송 가능 상태를 확인한다.
3. 혼잡 상태가 지속되면 전송할 청크 수를 줄이고, 안정적인 상태가 유지되면 늘린다.
4. 클라이언트가 스냅샷 데이터를 수신한다.
5. 수신 데이터의 복셀 생성 작업을 청크 단위로 나누어 비동기적으로 여러 프레임에 걸쳐 처리한다.
6. 필요한 복셀 생성 작업이 끝나면 스냅샷의 실제 월드 반영이 완료된다.

액터 생성과 소유권 복제는 위 목록의 마지막에 새로 시작되는 단계가 아니라 별도로 전달되는 정보다.
복셀 전송 부하를 낮춰 이 정보의 전달 지연을 완화했다.

스냅샷 데이터 수신 완료와 실제 월드의 복셀 생성 완료도 구분해 기록해야 한다.
수신 진행률이 끝났더라도 분산 처리 중인 생성 작업은 남아 있을 수 있다.
